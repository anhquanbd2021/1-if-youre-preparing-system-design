Engine-class guide

A filter, not a podium

The matcher treats database selection like a WHERE clause: workload properties in, class verdicts out. A class is fit when it covers every requirement natively, a stretch when a requirement is met by bolt-on or engineering effort, and a mismatch when a requirement is missing outright.

Claims vs. scores. Every named engine carries the source post's comparison as a claim — the lab never asserts those picks as fact. The capability numbers are illustrative teaching values, not measured benchmark data.

The inputs

Ten workload properties

Property

multi-record ACID writes

Money moves, inventory — all-or-nothing across rows. The consistency axis.

Property

sub-ms point lookups

One key in, one value out, at huge volume. Sessions, carts, rate limits.

Property

relational joins

Normalized tables joined in the serving path — not scan-speed joins.

Property

variable document records

Nested, schema-flexible records that differ row to row.

Property

multi-hop traversal

Friends-of-friends, path finding — edges are the query.

Property

append-only event ingest

Time-ordered writes that never update — metrics, logs, IoT.

Property

analytical scans & aggregates

Read millions of rows, aggregate, return one number — the OLAP axis.

Property

vector similarity search

Nearest-neighbor over embeddings — semantic search, RAG.

Property

distributed write scale

Write throughput beyond one node — many writers, not read replicas.

Property

open-format files

One copy on object storage, many engines over it — SQL + ML.

The punchline

Watch the traps fire

Keep the friend-of-friend recommendations workload and route it to the document class — the audit returns traversal: missing. Then route company-wide BI dashboards to the relational row store: analytics: missing. Same "good databases," two different ways to lose — and nothing a "top databases" list could have warned you about.

The inverse trap is subtler: route semantic product search to the row store and it comes back stretch, not mismatch — pgvector is a real partial. Whether that stretch is enough is a scale question, which is exactly the post's Pinecone-over-pgvector point.

Limits

What this demo does not claim

  • Capability levels are illustrative teaching values, not measurements — real engines move between releases.
  • Classes blur in practice: NewSQL is distributed OLTP, MongoDB has $graphLookup and Atlas Vector Search, TimescaleDB is Postgres under the hood. The filter is the lesson; the matrix is the example.
  • Instance names carry the source post's comparisons — labeled as claims, not verified picks.
  • Cost modeling, ops burden, and ecosystem maturity are deliberately out of scope — they are instance-level questions that arrive after the class decision.
